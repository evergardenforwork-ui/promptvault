# Project Docs Bootstrap

Создаёт (или, если уже существуют, — читает и опирается на них) пять контекстных
документов проекта: PRD.md, DESIGN.md, ARCHITECTURE.md, SCHEMA.md, RULES.md.
Это статичный контекст для любого ИИ, работающего над проектом — не агенты и не роли.

## Когда НЕ использовать этот skill

Если пользователь просит создать агентов, координатора, специалистов, AGENTS.md
с иерархией ролей — используй вместо этого skill `agent-architecture-bootstrap`.

Если нужны оба типа задач (новый проект с нуля): сначала выполни этот skill
(документы дают контекст), затем agent-architecture-bootstrap (агенты читают эти
документы как источник истины).

## Алгоритм

### 1. Проверь, что уже есть

Посмотри в корне проекта, существуют ли уже `PRD.md`, `DESIGN.md`, `ARCHITECTURE.md`,
`SCHEMA.md`, `RULES.md` (в любом регистре/расположении, например в `docs/`).

- Если файл **уже существует** — не перезаписывай его молча. Прочитай, покажи
  пользователю краткое резюме и спроси, дополнить/обновить или оставить как есть.
- Если файла **нет** — создай его из соответствующего шаблона в `templates/`.

### 2. Заполняй шаблоны реальным содержанием, а не заглушками

Каждый шаблон в `templates/` — это скелет с разделами. Твоя задача — заполнить
разделы содержанием, специфичным для ЭТОГО проекта:

- Если у тебя уже есть контекст из разговора (пользователь описал проект, стек,
  функции) — используй его.
- Если для конкретного раздела не хватает информации (например, нет данных для
  таблиц SCHEMA.md, потому что БД ещё не спроектирована) — спроси пользователя
  коротко по существу, вместо того чтобы писать "TODO" или выдумывать данные.
- Не создавай все 5 файлов только потому что попросили один — создавай только
  то, что просил пользователь (напр. просил только PRD — не трогай остальные 4,
  но упомяни, что есть DESIGN/ARCHITECTURE/SCHEMA/RULES, если это релевантно).

### 3. Не трогай существующий AGENTS.md/CLAUDE.md вслепую

После создания документов (или если они уже были) убедись, что любой ИИ, начинающий
работу в проекте, знает о них. Проверь, есть ли в корне AGENTS.md/CLAUDE.md/GEMINI.md:

- Если есть и там уже есть секция про эти документы — ничего не делай.
- Если есть, но секции нет — допиши в конец (НЕ переписывай остальное содержимое)
  блок:

```markdown
## Project Docs
Перед началом любой задачи в этом проекте свериться с:
- PRD.md — цели, MVP, scope, метрики успеха
- DESIGN.md — дизайн-система, брендинг, темы
- ARCHITECTURE.md — архитектура системы, потоки данных
- SCHEMA.md — схема БД и API
- RULES.md — стандарты кода (naming, SOLID/DRY/KISS)
```

- Если файла AGENTS.md/CLAUDE.md нет вообще — не создавай его в рамках этого skill
  (это не его ответственность). Просто сообщи пользователю, что документы созданы,
  и предложи использовать agent-architecture-bootstrap, если нужен файл-контекст
  для агентов.

### 4. Обновляй список при повторных вызовах

Если пользователь просит добавить/изменить раздел в уже существующем файле —
редактируй точечно (конкретный раздел), не переписывай файл целиком.

## Шаблоны

Полные шаблоны с разделами лежат в `templates/`:

- `templates/PRD.md` — Product Requirements Document
- `templates/DESIGN.md` — Design System
- `templates/ARCHITECTURE.md` — System Architecture
- `templates/SCHEMA.md` — Database & API Schema
- `templates/RULES.md` — Coding Standards & Architecture Rules

Прочитай нужный файл из `templates/` перед созданием соответствующего документа —
не воспроизводи структуру по памяти, структура может обновляться.

## Финальная проверка

- [ ] Создавались/обновлялись только те файлы, которые релевантны запросу
- [ ] Ни один раздел не оставлен как пустой "TODO" без попытки заполнить или спросить
- [ ] Существующие файлы не перезаписаны без подтверждения пользователя
- [ ] Существующий AGENTS.md/CLAUDE.md (если есть) дополнен секцией Project Docs,
      а не переписан
- [ ] SCHEMA.md соответствует реальным таблицам/роутам проекта, а не общему примеру
- [ ] RULES.md отражает реальный стек проекта (напр. TypeScript-раздел не нужен,
      если проект не на TS/JS)
