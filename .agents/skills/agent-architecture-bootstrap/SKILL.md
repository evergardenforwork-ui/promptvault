# Agent Architecture Bootstrap

Создаёт структуру ролей ИИ-агентов под конкретную задачу: координатор + специалисты,
их skills, файл контекста AGENTS.md и установочные файлы.

## Когда НЕ использовать этот skill

Если пользователь просит создать PRD.md, DESIGN.md, ARCHITECTURE.md, SCHEMA.md или
RULES.md — это НЕ агенты, это статичная документация проекта. Используй вместо этого
skill `project-docs-bootstrap`. Признаки: "продуктовые требования", "дизайн-система",
"схема базы данных", "coding standards", "product scope".

Если оба типа задач нужны одновременно (новый проект с нуля) — можно использовать оба
skill'а последовательно: сначала документацию (project-docs-bootstrap), затем агентов
поверх неё (этот skill), т.к. агентам может понадобиться контекст из PRD/ARCHITECTURE.

## Шаг 0. Определи имя конфиг-папки

Разные CLI-инструменты ищут разные скрытые папки конфигурации в корне проекта:

| Инструмент          | Папка                |
|----------------------|-----------------------|
| opencode             | `.opencode/`          |
| Gemini CLI           | `.gemini/`            |
| Grok CLI             | `.grok/`              |
| Claude Code          | `.claude/`            |
| другой / неизвестно  | спроси пользователя, какой CLI он использует |

DEFAULT (если не удалось определить): `.agent/`

Дальше используется плейсхолдер `{AGENT_DIR}` — замени его на реально определённое
имя папки во ВСЕХ путях ниже.

## Шаг 1. Структура папок и файлов

```
project/
├── AGENTS.md
├── README.md
├── install.sh
├── {AGENT_DIR}.json.example
└── {AGENT_DIR}/
    ├── agent/
    │   └── <агенты, реально нужные ПОД ЭТУ задачу>   ← см. Шаг 4, НЕ хардкод
    └── skills/
        ├── <skill-name-1>/SKILL.md                    ← см. Шаг 5
        └── ...
```

## Шаг 2. Важно: не трогай существующий AGENTS.md/CLAUDE.md вслепую

Прежде чем создавать AGENTS.md — проверь, существует ли он уже в корне проекта
(или CLAUDE.md/GEMINI.md и т.п.). Если файл уже есть:

- **НИКОГДА не перезаписывай и не удаляй существующее содержимое.** Оно может
  содержать важный контекст проекта, скачанный вместе с шаблоном/репозиторием.
- Допиши в конец файла новую секцию `## Иерархия агентов в этом проекте` (если такой
  секции ещё нет) — только с описанием ролей из Шага 4.
- Если в файле уже есть похожая секция про агентов — спроси пользователя, заменить
  её или оставить обе.

Если файла нет — создай новый по шаблону ниже.

### Содержимое `AGENTS.md`

```markdown
# AGENTS.md

## О проекте
[Заполни: что за проект, домен, цель — спроси пользователя, если не указано]

## Правила для ЛЮБОГО агента, работающего в этом проекте
- [конвенции, ограничения, что нельзя трогать/менять]
- [формат ответов, стиль, язык общения]
- [где лежат ключевые файлы/данные проекта]

## Иерархия агентов в этом проекте
[Автоматически заполняется по Шагу 4: имя координатора + список специалистов,
реально созданных под эту задачу — без заглушек]

## Список доступных skills
[Автоматически заполняется по мере добавления скиллов в {AGENT_DIR}/skills/]
```

## Шаг 3. Содержимое `README.md` (для человека, не для ИИ)

```markdown
# [Название проекта]

[Одно предложение — что это]

## Агенты

[Таблица реально созданных агентов из Шага 4 — только тех, что нужны именно
этому проекту]

| Агент | Роль | Ключевая черта |
|---|---|---|

## Skills

| Skill | Когда активируется |
|---|---|
| [заполнить по мере создания] | [триггеры] |

## Установка

\`\`\`bash
./install.sh
cp {AGENT_DIR}.json.example ~/.config/{AGENT_DIR}/config.json
\`\`\`

## Использование

Обратись к координатору напрямую (см. таблицу выше), он сам решит, кого из
команды подключить:

\`\`\`
@<имя-координатора>: [твоя задача]
\`\`\`
```

## Шаг 4. Определи, какие агенты реально нужны — и только потом создай их

Не создавай агентов "по умолчанию" (orchestrator/researcher/implementer/critic — это
ПРИМЕРЫ паттерна, а не обязательный список). Сначала проанализируй задачу пользователя
и реши, какие роли ей реально требуются. Может понадобиться 2 агента, может 6 —
зависит от домена.

Единственное жёсткое правило: если ролей больше одной, среди них должен быть **ровно
один координатор**, который делегирует и синтезирует, но сам не выполняет
специализированную работу. Называй его по смыслу проекта — не обязательно
"orchestrator", может быть "manager", "editor-in-chief", "lead" и т. п.

Примеры (только для референса, не создавай их вслепую):

| Домен | Координатор | Специалисты (пример) |
|---|---|---|
| Разработка | orchestrator | researcher, implementer, critic |
| Юр. отдел | case-manager | contract-analyzer, precedent-search, risk-assessor |
| Копирайтинг | editor | strategist, drafter, seo-checker |
| Поддержка клиентов | support-coordinator | classifier, kb-agent, escalation |
| Финансы | coordinator | market-analyst, risk-manager, report-writer |

Если из запроса пользователя неясно, какие роли нужны — спроси коротко, прежде чем
создавать файлы, вместо того чтобы ставить заглушки-агенты, которые никто не просил.

Каждый агент — отдельный `.md` файл с frontmatter + телом:

```markdown
---
name: <короткое-имя>
role: <кто он одной фразой>
model: DEFAULT (унаследовать от глобального конфига, не хардкодить)
---

# <Имя роли>

## Role
[2-3 предложения: экспертиза, стиль мышления, чем отличается от других агентов]

## Goal
[Одна главная цель. Если целей несколько — раздели на отдельных агентов]

## Context needed
[Что оркестратор обязан передать этому агенту для работы]

## Output format
[Строгий формат ответа для лёгкого синтеза оркестратором, например:]
\`\`\`
## Findings
- ...
## Confidence: [high/medium/low]
## Open questions
- ...
\`\`\`

## When NOT to use this agent
[В каких случаях задача не по его профилю — какого агента звать вместо]
```

Создай столько агентов, сколько реально нужно под задачу — не больше и не меньше.

## Шаг 5. Содержимое каждого `{AGENT_DIR}/skills/<name>/SKILL.md`

```markdown
---
name: <skill-name>
description: <когда именно активировать этот skill — конкретные триггеры/ключевые слова>
---

# <Название skill>

## Когда применять
[Конкретные ситуации/фразы, по которым агент должен догадаться загрузить этот skill]

## Инструкции
[Пошаговая экспертиза/чеклист/паттерн — то, что агент должен применить]

## Пример
[Краткий пример входа и выхода]
```

Правило активации: агент должен явно вызывать инструмент загрузки skill
(`Skill`/`load_skill`), если такой инструмент доступен в среде. Если инструмента
нет — агент обязан вручную прочитать файл skill перед тем как отвечать по теме,
которая совпадает с description. Просто описания skill в промпте недостаточно —
нужен явный шаг "прочитать/загрузить".

## Шаг 6. Содержимое `install.sh`

```bash
#!/bin/bash
set -e
mkdir -p ~/.config/{AGENT_DIR}/agent
mkdir -p ~/.config/{AGENT_DIR}/skills
cp -r {AGENT_DIR}/agent/*.md ~/.config/{AGENT_DIR}/agent/
cp -r {AGENT_DIR}/skills/* ~/.config/{AGENT_DIR}/skills/
echo "Установлено в ~/.config/{AGENT_DIR}/"
```

## Шаг 7. Содержимое `{AGENT_DIR}.json.example`

```json
{
  "default_agent": "<имя-координатора>",
  "agent": {
    "<имя-координатора>": {},
    "<имя-специалиста-1>": {},
    "<имя-специалиста-2>": {}
  }
}
```

## Шаг 8. Финальная проверка перед завершением

- [ ] Все `{AGENT_DIR}` заменены на реальное имя папки
- [ ] Существующий AGENTS.md/CLAUDE.md не перезаписан — только дополнен
- [ ] `AGENTS.md` не дублирует роли агентов текстом — только структурой из Шага 4
- [ ] `README.md` содержит таблицу агентов и таблицу skills
- [ ] Созданы только те агенты, что реально нужны под задачу (без заглушек "на всякий случай")
- [ ] У координатора явно написано "никогда не выполняет работу сам"
- [ ] Минимум 1 реальный skill создан под конкретную задачу пользователя (не заглушка)
- [ ] Если платформа не поддерживает реальный spawn суб-агентов отдельным вызовом —
      добавь в AGENTS.md примечание с fallback-паттерном "роли внутри одного ответа"
- [ ] Если CLI — не Claude Code (нет автодискавери user-level skills), добавлена
      секция "Available Skills" с путями к обоим skill'ам (agent-architecture-bootstrap
      и project-docs-bootstrap), если они установлены глобально
